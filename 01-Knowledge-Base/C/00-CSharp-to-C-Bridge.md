# C# → C → Embedded C：给上位机开发者的过渡桥

## 为什么需要这一关

如果你已经会用 C# 写上位机，很多“程序对象”的直觉在桌面软件里是安全的：

```text
对象
→ 属性
→ 方法
→ 垃圾回收
→ 异常
→ 操作系统保护
```

进入嵌入式 C 后，同样的功能会被拆成：

```text
值
→ 地址
→ 指针
→ 内存布局
→ 生命周期
→ 寄存器
→ 真实引脚
```

这不是把 C# 忘掉，而是把原来的高层模型逐层打开。

## 第一组：值、引用和地址

| C# 直觉 | C 的对应物 | 嵌入式含义 |
|---|---|---|
| `int x = 10` | `int x = 10` | 一个对象占据一段内存 |
| `ref` / 引用 | 指针 `int*` | 传递地址，可能直接改变目标 |
| 对象引用 | 指针值 | 指针本身也是一个变量 |
| 属性访问 | 读写表达式 | 最终可能变成多次内存访问 |
| `null` | `NULL` / 无效地址 | 解引用前必须确认地址有效 |

C# 的引用由运行时管理。C 的指针只是一个数值形式的地址，编译器不会替你证明它指向正确对象。

```c
int value = 10;
int *p = &value;
*p = 20;
```

这里 `p` 保存的是地址，`*p` 才是访问地址所指向的内容。

## 第二组：数组边界

C# 数组通常携带长度信息，并在越界时抛出异常。

C 数组通常只是连续内存：

```c
uint8_t buffer[4];
buffer[0] = 1;
buffer[3] = 4;
```

下面的写法可能破坏其他对象：

```c
buffer[4] = 5;
```

在 MCU 中，越界可能表现为：

- 另一个变量被修改；
- 外设配置被破坏；
- 程序进入 HardFault；
- 故障只在优化或特定时序下出现。

因此嵌入式调试不能只问“代码有没有执行”，还要检查地址、长度和实际内存。

## 第三组：GC、栈、堆和静态区

C# 的 GC 会管理托管对象的回收时机。C 没有自动 GC：

```text
局部变量       → 通常位于栈
static/global  → 静态存储区
malloc         → 堆，必须明确释放
寄存器地址     → 固定的硬件映射地址
```

在 MCU 中，堆不是默认的万能方案。动态分配可能带来碎片、不可预测的失败和实时性问题。

先掌握：

```text
对象是谁创建的？
对象活多久？
谁负责释放？
访问时地址是否仍然有效？
```

## 第四组：class、struct 和数据布局

C# 的 `class` 是引用语义对象，`struct` 默认是值语义数据结构。C 的 `struct` 主要描述一段连续内存布局：

```c
struct SensorSample {
    uint16_t raw;
    uint16_t status;
};
```

需要继续追问：

- 每个成员占多少字节？
- 是否存在 padding？
- 发送到总线时字节顺序是什么？
- 指针指向的是整个结构，还是某个成员？
- 这个布局是否与协议或外设要求一致？

在 C# 中序列化通常由库帮助完成；在嵌入式 C 中，布局本身就是协议和硬件证据的一部分。

## 第五组：readonly、const 和 volatile

这些词不能直接一一翻译：

- `const`：限制当前代码通过某个表达式修改对象；
- `volatile`：告诉编译器，每次访问都可能观察到外部变化；
- C# `readonly`：限制字段写入时机，语义与 C `const` 不同；
- `volatile` 不是线程锁，也不是原子操作。

MCU 外设寄存器、ISR 与主循环共享的状态，可能需要 `volatile`，但是否安全仍要分析访问宽度、原子性和并发关系。

## 第六组：异常、返回值和错误证据

桌面程序常用异常表达失败：

```csharp
try
{
    ReadDevice();
}
catch (Exception ex)
{
    Log(ex);
}
```

裸机 C 常见形式是显式返回值：

```c
int status = read_device(&sample);
if (status != 0) {
    record_error(status);
}
```

这要求调用者明确处理：

```text
函数是否成功？
输出 Buffer 是否有效？
错误码表示哪一层失败？
是否需要重试？
硬件状态是否已经改变？
```

错误码不是“没有异常所以成功”。它必须与可观察证据对应。

## 第七组：从 C# API 到 MCU 寄存器

C# 上位机可能调用：

```csharp
device.SetOutput(true);
```

MCU 低层代码可能最终做：

```c
#define GPIO_OUT (*(volatile uint32_t *)0x40020014U)
GPIO_OUT |= (1U << 5);
```

这段代码需要拆成：

```text
固定地址
→ 指针类型转换
→ volatile 访问
→ 解引用
→ 读取寄存器
→ 设置 bit
→ 真实引脚电平
```

不要把它当成“神秘的嵌入式写法”。它只是把高层 API 隐藏的硬件路径展开了。

## 迁移检查表

当你从 C# 进入 C 时，每遇到一个新概念都回答：

1. 这个数据实际存在哪里？
2. 谁拥有它？
3. 它的生命周期多长？
4. 谁负责检查边界？
5. 谁负责报告错误？
6. 这个值最终是否会影响地址、时序或硬件状态？
