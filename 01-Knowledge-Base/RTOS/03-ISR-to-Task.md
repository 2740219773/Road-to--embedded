# ISR → Task — 中断发生后，为什么不把所有工作都放在中断里？

## 先说人话

ISR 是中断发生后 CPU 立即去执行的一小段处理代码。

它适合做“快而短”的事情，例如：

- 记下一个事件发生了；
- 读取一个必要状态；
- 把数据放进 Queue；
- 唤醒某个 Task。

不适合在 ISR 里长时间打印、等待、做复杂计算或执行可能阻塞的操作。

## 典型模式

```text
Hardware Event
↓
ISR
↓ 只做最必要处理
Queue / Semaphore / Notification
↓
Task 被唤醒
↓
完成较重工作
```

## 为什么这样分？

ISR 运行时间越长，其他中断和任务越容易被延迟，整个系统的实时性会变差。

## 初学者常见误区

- 在 ISR 里直接做完整业务；
- 在 ISR 中使用普通 Task API，而不是 RTOS 提供的 FromISR 版本；
- ISR 里发送大量日志；
- ISR 与 Task 共享变量，却没有设计清楚所有权和同步方式。

## 目标

看到一个中断需求时，先问：

> 哪部分必须立刻做？哪部分可以交给 Task 稍后做？
