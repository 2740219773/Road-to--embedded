# Content Design Guide

## 核心原则

Road to Embedded 不再默认使用“长篇 Markdown + 示例代码”作为课程形式。

新增内容前先问：

> 这个知识最适合通过什么现象被理解？

## 媒介选择矩阵

| 知识类型 | 推荐主媒介 | 辅助媒介 |
|---|---|---|
| 定义、边界、术语 | Markdown | Quiz |
| 地址、内存、指针 | 可视化/HTML | Mission |
| 位运算、寄存器 | 交互模拟器 | 真机 GPIO |
| GPIO | Mission + 真机 | Register Lab |
| PWM | 波形动画 + 示波器 | Markdown |
| UART | 帧可视化 + 真机 | 示波器/逻分 |
| SPI/I2C | 时序交互 | 真机故障挑战 |
| ADC | 采样可视化 | 真机波形 |
| 中断 | Timeline | 故障挑战 |
| DMA | 数据流动画 | 真机实验 |
| RTOS | Scheduler Timeline | OpenMAIC |
| Mutex/Deadlock | 竞争动画 | Debug Case |
| FPGA FSM | 状态机动画 | Verilog 仿真 |
| CDC/Timing | 时钟域可视化 | Vivado 分析 |

## 内容的四层表达

同一个知识点可以有四种不同深度，但职责不能混乱。

### A. Hook

只负责让学习者产生问题。

例如：

> 明明只想打开一个 LED，为什么另外三个灯突然灭了？

### B. Mental Model

用图、动画、类比建立直觉。

### C. Engineering Truth

回到准确技术定义。这部分通常链接 Knowledge Base。

### D. Transfer

把知识迁移到真实硬件、故障或新场景。

## 长文本控制

学习者主线中的单个连续文字块应尽量短。

如果一个页面需要连续解释很多段，应判断是否应该拆成：

- 图；
- 流程图；
- 表格；
- Quiz；
- 互动；
- 多个小关卡；
- Knowledge Base 链接。

Knowledge Base 可以比 Mission 更完整，但仍避免为了“显得全面”而重写教材。

## 互动设计不是装饰

不要只做：

- 点击下一页；
- 无意义积分；
- 背定义选择题；
- 换成卡通风但内容不变。

高价值互动应该改变学习者的认知过程，例如：

- 先预测再显示结果；
- 拖动参数观察波形；
- 点击 bit 看寄存器数值变化；
- 故意配置错误波特率；
- 给出多个故障假设，让学习者选择验证手段；
- 根据证据逐步排除原因。

## Mission 命名

优先使用“问题 + 情境”，减少教材章节感。

差：

```text
03 位运算
04 UART
05 DMA
```

好：

```text
Bit Hacker — 为什么只开一个 LED 却清掉了其他位？
Lost Signal — MCU 为什么一直收不到串口数据？
CPU Vacation — 不让 CPU 搬数据，DMA 怎么完成传输？
```

中文标题应清楚，英文副标题可以增加识别度，但不要为了酷而牺牲含义。

## 故障设计

每个故障必须有“可观察证据”。

差：

> 程序有 Bug，请修复。

好：

```text
现象：串口输出乱码
已知：MCU 配置 115200
证据：示波器测得单 bit 时间约 17.36 μs
任务：判断真正波特率并找到配置问题
```

## Quiz 设计

优先级：

1. Prediction：下一步会发生什么；
2. Diagnosis：哪个证据最有价值；
3. Transfer：换一个场景还能不能判断；
4. Concept：概念检查；
5. Memory：纯记忆题。

## AI 教学角色

AI Teacher：准确、短解释。

Rookie Engineer：提出真实初学者误区。

Debug Mentor：不给直接答案，先问证据和验证方式。

Project Lead：提出需求、约束、验收标准。

Reviewer：检查学习者是否真正理解，而不是只得到正确输出。

## 一节核心课程的验收

至少检查：

- 学习者为什么会想继续？
- 是否必须读长文才能推进？
- 是否有一次预测？
- 是否有一次实际操作？
- 是否有可观察结果？
- 是否有典型错误？
- 是否要求使用证据调试？
- 是否连接真实工程？
- 是否有明确完成标准？
