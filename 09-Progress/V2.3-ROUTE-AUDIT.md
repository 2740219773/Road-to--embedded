# V2.3 Whole-Project Route Audit

## Audit Goal

Stage 02 内容写完后，重新检查整个项目是否仍符合最初制定的学习方向，避免出现“内容越写越多，但路线逐渐变成知识堆积”的问题。

本次检查覆盖：

- `PROJECT.md`；
- `README.md`；
- `ROADMAP.md`；
- `docs/ARCHITECTURE.md`；
- `docs/DEVELOPMENT-PLAN.md`；
- Stage 00～08 Learning Path 职责；
- V2.3 Stage 02 新增内容；
- Stage 02 与 Stage 03 的边界。

## Original Direction

项目最终目标始终不是“成为某一种 MCU API 教程”，而是建立一条跨层工程成长路线：

```text
System View
→ C / Memory
→ Real MCU Foundation
→ MCU Peripherals
→ Debugging
→ RTOS
→ Embedded Linux
→ FPGA
→ PC / MCU / Linux / FPGA System Integration
```

学习方式应始终保持：

```text
Problem / Phenomenon
→ Predict
→ Observe
→ Explain
→ Real Evidence
→ Break It
→ Debug
→ Boss
→ Transfer
```

## Findings

### 1. Overall Learning Direction — PASS

Stage 顺序仍保持 00～08，没有出现为了内容方便而打乱主线的情况。

Stage 01 从 C 语法课变成 Memory / Pointer / Register / Linker 的底层模型，Stage 02 再连接真实 MCU，这个演进符合原始方向。

### 2. Stage 02 Scope — PASS after correction

Stage 02 当前聚焦：

```text
Bring-up
GPIO
Clock
Debugger
Interrupt
Timer
PWM
Physical Pin
Voltage / Waveform
Instrument Evidence
```

没有继续扩成 UART / SPI / I2C / ADC 大全，符合“先把真实硬件基础打牢”的教学原则。

### 3. Stage 02 / Stage 03 Boundary — ISSUE FOUND, FIXED

发现原 Stage 03 仍把 PWM 写在主线中，而 V2.3 Stage 02 已正式承担 PWM 基础和真机测量。

修订后：

```text
Stage 02 = MCU Foundation
Stage 03 = Peripheral Expansion
```

PWM 基础属于 Stage 02，Stage 03 只按项目需要复用。

### 4. V2.3 Roadmap vs Stage Model — ISSUE FOUND, FIXED

原 ROADMAP 的 V2.3 同时列 GPIO、Timer 和 UART/ADC/SPI/I2C/DMA，看起来像一个阶段必须全部完成；实际 Learning Path 已经拆成 Stage 02 和 Stage 03。

没有修改总版本方向，而是把 V2.3 明确拆成：

```text
Phase A — Stage 02 MCU Foundation
Phase B — Stage 03 Peripheral Engineer
```

这样既不放弃 V2.3 原目标，也避免新手负荷过大。

### 5. Governance Drift — ISSUE FOUND, FIXED

README、PROJECT、ARCHITECTURE、DEVELOPMENT-PLAN 和部分后期 Stage 仍残留 V2.1/P0 文案。

这说明内容开发速度再次超过治理文档更新速度。

已更新 Source of Truth 和 Living Plan，并要求后续每个版本合并前检查版本状态一致性。

### 6. Debugging Position — PASS

Stage 02/03 每关继续包含故障注入和证据驱动调试，但 Stage 04 仍保留“系统性调试能力”的独立职责。

这两者不冲突：

```text
Stage 02/03 = 在开发中学会基本排错
Stage 04 = 把 Debugging 本身提升为独立工程能力
```

### 7. RTOS Position — PASS

Stage 05 仍建立在多外设裸机节点之后，再进入 Task / Scheduler / Queue / Race / Deadlock。

没有出现“还不会裸机系统就直接 FreeRTOS API”的顺序倒置。

### 8. Embedded Linux Position — PASS

Stage 06 仍从 MCU 扩展到完整 OS 系统分层，现有内容明确标为 vertical-slice prototype，当前 V2.3 不继续扩张。

### 9. FPGA Position — PASS

Stage 07 仍强调“FPGA 不是更快的 MCU”，主目标是从顺序软件思维迁移到并行数字逻辑。

没有因为用户最终目标包含 FPGA 就过早跳过 MCU / Debug / RTOS 基础。

### 10. System Integration End Goal — PASS

Stage 08 仍保留：

```text
PC / 上位机
↕
Network / Bus
↕
MCU / Linux
↕
FPGA
↕
Real Device
```

与项目最初“上位机会、下位机会、最终形成跨层能力”的方向一致。

## Main Risk Identified

当前最大的路线风险不是“技术学错了”，而是：

> 内容扩张速度大于学习闭环和治理更新速度。

如果不控制，项目很容易再次变成一个“资料很多，但不知道该怎么学”的仓库。

因此后续增加 Guardrail：

```text
一个 Stage 的当前闭环没验收
→ 不横向扩下一个 Stage

一个主题只有 Knowledge/API
→ 不算课程完成

版本说明落后于真实内容
→ 先修治理，再继续扩张
```

---

## Final Conclusion

**当前项目没有发生方向性偏离。**

V2.1 建立架构，V2.2 验证 C/Memory 互动闭环，V2.3 正把虚拟底层模型接到真实 MCU；后续 Debugging → RTOS → Linux → FPGA → System Integration 的顺序仍然成立。

本轮需要修正的是 Stage 边界和治理文档，而不是推翻课程路线。

下一步应先完成 V2.3 Phase A 的零基础走查、链接/术语检查和 PR 验收，再进入 Phase B Stage 03。
